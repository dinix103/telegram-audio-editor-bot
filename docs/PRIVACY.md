# Хранение и очистка

## Рабочие данные редактора

`/work/jobs/<uuid>/` содержит исходники, подготовленную обложку и результаты. Это временный
volume, который **нельзя включать в бэкапы или снапшоты**. Доступ имеют только bot, worker,
cleanup. Каждая сессия принадлежит Telegram user ID и работает только в личном чате.

- После успешной доставки — немедленное удаление всей рабочей сессии.
- При ошибке/отмене worker — удаление после завершения дочернего процесса.
- После 15 минут бездействия — удаление с точностью до 30-секундного прохода cleanup.
- Незавершённые каталоги без активности — удаление при возрасте более часа.
- Lease/heartbeat защищают обработку и отправку от удаления. После аварии защита
  истекает; очистка выполняется после определения неактивности.
- `/delete` дополнительно удаляет PostgreSQL-настройки пользователя и FSM-состояние.

Redis хранит user/chat ID, сведения аудио и правки только на время задачи. Дисковая
персистентность Redis выключена. Настройки PostgreSQL связаны с user ID; счётчики задач
агрегированы по дню и классу результата без user ID.

## Кэш собственного Bot API — отдельные данные

Volume `/telegram` принадлежит официальному серверу. Редактор монтирует его только
для чтения. **Обычный cleanup не удаляет оттуда ничего**, поскольку удаление файлов
работающего Bot API может повредить его состояние.

Сервер может продолжать хранить загруженные вложения после удаления рабочей копии.
Поэтому бот не обещает, что `/delete` удалит все копии на сервере Telegram API.
Оператор должен регулярно выполнять отдельную offline-ротацию, например ежедневно
в окно обслуживания, и контролировать размер volume. Автоматической выборочной
очистки живого кэша по выдуманному TTL нет.

Безопасная процедура для **выделенного этому боту** volume:

1. `/admin pause`, дождаться нулевой очереди и завершения отправок; незавершённые
   пользовательские сессии завершить или дождаться TTL. Убедиться, что никто другой
   не использует этот Bot API / volume.
2. Остановить приложение, workers и сервер одной командой `docker compose stop`.
   PostgreSQL volume сохраняется. Сервер должен полностью завершиться.
3. Запустить offline-helper; он проверяет недоступность сервера и работает исключительно
   с `/telegram` в отдельном контейнере:

```bash
docker compose -f docker-compose.yml -f docker-compose.maintenance.yml \
  --profile maintenance run --rm --no-deps api-cache-maintenance --confirm-server-stopped
```

4. `docker compose up -d`, проверить `getMe`, загрузку небольшого файла, затем `/admin resume`.

Эта операция удаляет весь локальный кэш и служебное состояние только остановленного
выделенного Bot API. Сервер заново инициализирует его при запуске. Процедуру необходимо
проверить на тестовом сервере перед эксплуатацией; не применять к общему серверу других ботов.
Для переноса бота на другой Bot API используйте официальную процедуру `close`/`logOut`,
а не эту очистку. Локальная очистка не удаляет сообщения в Telegram и файлы на устройствах.

## Эксплуатационные условия

Не подключайте файловые каталоги к антивирусным облачным загрузкам, системам аналитики,
AI-обучению, централизованному сбору вложений или резервному копированию. Хостовый
администратор технически имеет доступ к диску; бот не предоставляет ему аудио через UI.
Выдавайте доступ к хосту только доверенным операторам. Политика приложения не может
управлять копиями, уже сохранёнными Telegram или самими пользователями.
